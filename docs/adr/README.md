# 架构决策记录（ADR）

本目录记录 HysialX 的**不可逆或有争议的技术选型**：为什么这么定、代价是什么、
什么条件下应该重审。教程与设计文档讲"怎么做"，ADR 讲"为什么是它、而不是别的"。

## 什么时候该写 ADR

满足任一条就值得写：

- 选型会**影响插件作者的写法**（接口契约级）；
- 存在**安全或正确性**上的取舍，且事后改代价高；
- 有多种合理方案，团队里可能反复争论（写过一次就不用再吵）；
- 需要记录**重审触发条件**（现在这样选是因为当下约束，条件变了要回来改）。

不必写 ADR：局部实现细节、可随时替换的库、纯样式约定（那些放教程/README）。

## 模板（复制后填写）

```markdown
# ADR-XXXX：<一句话标题>

| 项 | 值 |
| --- | --- |
| 状态 | 提议（Proposed）/ **已采纳（Accepted）** / 已废弃（Deprecated）/ 被 ADR-XXXX 取代（Superseded） |
| 日期 | YYYY-MM-DD |
| 决策者 | |
| 影响范围 | 受影响的文件/模块 |
| 相关文档 | 设计文档、教程、其他 ADR |

## TL;DR
3–5 条，让人 30 秒内知道结论。

## 1. 背景（Context）
客观事实：协议/依赖的现状、现有资产与调用点（给文件:行号）、约束、风险。

## 2. 决策（Decision）
编号列出 D1/D2/…，每条都是可执行、可验证的（"必须/一律/禁止"，不要写"建议"）。

## 3. 理由（Rationale）
场景 → 选择 → 原因 的表格；把"为什么不是另一个"说清。

## 4. 后果（Consequences）
正面 / 负面与成本 / 必须配套的强制项。负面要写实，否则 ADR 没有价值。

## 5. 备选方案（Alternatives）
每个方案：内容 + 拒绝或采纳的理由 + （若拒绝）什么条件下应该改选。

## 6. 执行与验证（Enforcement）
代码约定表、回归测试用例（输入 → 期望）、review checklist。

## 7. 重审触发条件（Revisit triggers）
可观测的、具体的条件（事故、依赖弃用、数量阈值…），不要写"以后再看"。

## 8. 参考
官方文档、规范链接、项目内相关章节。
```

## 约定

- **一个 ADR 只做一个决策**，别把三个选型塞进一篇。
- **决策写"必须"不写"建议"**：含糊的 ADR 等于没写。
- **不改旧 ADR 的正文**：结论变了就新写一篇，把旧篇状态改成"被 ADR-XXXX 取代"。
- 与教程/设计文档**互相链接**：ADR 里链到 §章节，教程里在相关决策点链回 ADR。
